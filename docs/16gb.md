# chad on a 16 GB Mac

Upstream chad targets a 24 GB MacBook Pro. This fork also runs on a 16 GB MacBook Air
or Mac mini, by choosing a build of the model that fits.

## What changes on 16 GB

| | 24 GB and up | 16 GB |
|---|---|---|
| Default model | Qwen3.8-27B, Unsloth `UD-Q3_K_XL` GGUF | The same Qwen3.8-27B as Prism ML's ternary Bonsai 2 pack |
| Weights resident | ~13.2 GB | ~8 GB |
| Download | ~14 GB, plus a ~13 GB converted copy | ~9 GB, no converted copy |
| Free disk for the first run | ~30 GB | ~11 GB |
| Context before compaction | ~74k tokens on 24 GB | ~40k tokens |
| Drafter | DFlash2 | DFlash2 (bundled in the pack) |

Nothing needs configuring. `chad`, `chad prove`, `chad-bench` and `chad-serve` read the
machine's RAM and pick the build: under 24 GB they load
[`nathansutton/Qwen3.8-27B-Ternary-Bonsai-2-DFlash2-MLX`](https://huggingface.co/nathansutton/Qwen3.8-27B-Ternary-Bonsai-2-DFlash2-MLX).
The banner and the load line say which one was chosen and why.

`--model` and `CHAD_MODEL` still override the choice on any machine. Upstream's 14 GB
default does not fit in 16 GB: its weights alone leave nothing for the KV cache, and
macOS pages them.

## Install

The 16 GB default is in this fork, not in the `chad-code` package on PyPI:

```bash
uvx --from git+https://github.com/riteshdhemla/chad@mac-16gb chad          # the agent
uvx --from git+https://github.com/riteshdhemla/chad@mac-16gb chad prove    # smoke test
uvx --from git+https://github.com/riteshdhemla/chad@mac-16gb chad-serve    # for Pi, see pi.md
```

With upstream's package, `CHAD_MODEL=nathansutton/Qwen3.8-27B-Ternary-Bonsai-2-DFlash2-MLX
uvx chad-code` selects the same build by hand.

## What to expect

Measured on a base M5 MacBook Air with 16 GB, on battery. The Air has no fan, and that
shapes every number here more than memory does.

**Memory is not the constraint.** The engine holds about 9 GB (8.8 GB after load, a
10.5 GB peak while reading a 6,000-token prompt), inside the 12.7 GB macOS recommends
for the GPU on this machine. MLX's spare buffer cache stays near 0.2 GB, so there is
nothing to reclaim by capping it.

**Heat is.** On a fixed workload, decode fell from 39 to 29 tokens/second within one
minute of continuous load, and prompt reading from 168 to 126; after a four-minute rest
both were back. A Mac mini has a fan and should hold its speed longer, but that is not
measured here.

**Real agent tasks**, driven by Pi through `chad-serve`, one client, three minutes of
cool-down before each:

| Task | Thinking | Model calls | Output tokens | Wall time | Decode |
|---|---|---|---|---|---|
| Fix a failing test | on | 5 | 721 | 57 s | 14.7 to 24.1 tok/s |
| Write a module and its tests | on | 6 | 1,800 | 159 s | 19.4 falling to 7.5 tok/s |
| Rename a function across files | on | 5 | 794 | 58 s | 13.4 to 26.4 tok/s |
| Write a module and its tests | off | 5 | 725 | 55 s | 13.6 to 27.2 tok/s |
| Rename a function across files | off | 6 | 819 | 53 s | 14.5 to 29.9 tok/s |

All five finished with passing tests. Across them:

- The first prompt of a session (Pi's 1,600-token system prompt and tools) takes 9 to
  10 seconds to read. Every later step starts in about a second, because 81 to 87% of
  prompt tokens come from the prefix cache.
- Decode speed follows how much of each drafted block is accepted: 60 to 77% on tool
  calls and code (20 to 30 tok/s), 26 to 37% on prose and reasoning (13 to 15 tok/s).
- A task that runs past a minute or two slows as the machine warms: the module-writing
  task's last call decoded at 7.5 tok/s.

`chad-bench` reports 36 tokens/second decode on this machine. It is a ceiling: greedy
decoding of a tiled block of code, which the drafter predicts almost perfectly.

## Getting the most out of a 16 GB Air or mini

- **Turn thinking off for routine work.** Reasoning was 25 to 54% of the output tokens
  above, and on a heat-limited machine fewer tokens is the one lever that reliably buys
  time: the module-writing task took 55 seconds without thinking against 159 with.
  In chad that is `--no-think`; in Pi, `--thinking off` (see [pi.md](pi.md)). Keep it on
  for hard problems, where the model needs the reasoning to get the code right.
- **Keep tasks short and let the machine rest.** Speed is highest in the first minute.
  A few scoped asks beat one long one.
- **Plug in and keep the Mac on a hard surface.** Both help a fanless machine shed heat.
- **Quit memory-heavy apps first**, browsers above all. The context governor sizes the
  window from the memory that is free when the model loads.
- **Run one local model at a time.** A second engine (another `chad`, `chad-serve`, or
  an llama.cpp server) will not fit alongside this one.
- **One client per `chad-serve`.** Two agent sessions sharing a server take turns
  evicting each other's prompt cache, and every step re-reads its whole transcript.
- **Cap the window if the Mac swaps**: `CHAD_MAX_CONTEXT=24000` trades context for
  headroom.
